# V1.1.0 Merge: Home/Phone Module + Common Call Engine

This merges two builds that both started from the same V1.1.0 baseline and
diverged, each carrying real, non-overlapping work the other lacked:

- **AutoCallManager-v1_1_0-HomeReorder-PhoneModule.zip** ("A") -- Home screen
  reorder, redesigned header, and a brand-new Phone/Calls module
  (`PhoneActivity` + supporting files). Documented in `CHANGELOG_V1.1.0.md`.
- **AutoCallManager-v1.1.0-CALL-ENGINE-INTEGRATION.zip** ("B") -- the shared
  `CallExecutionManager.executeCallAttempt()` engine, `callSource`
  (MANUAL/SCHEDULED) tracing, granular AI Voice error codes, the AI Voice
  main-thread network fix, and removal of the old 6-second OFFHOOK
  false-failure gate. Documented in `V1.0.9-AI-VOICE-BACKEND-FIX.md` and
  `V1.1.0-CALL-ENGINE-INTEGRATION.md`.

Neither zip is a superset of the other. **A's copies of `CallExecutionManager.kt`,
`CallReceiver.kt`, `BootReceiver.kt`, and `AiVoiceCallClient.kt` predate B's
fixes entirely** (e.g. A's `AiVoiceCallClient.kt` is 55 lines; B's is 178 --
B's granular codes and background-thread fix were never in A's branch at
all). Confirmed by reading every changed file in full, not inferred from
either zip's own changelog.

## 3. THE CONFLICT: `PhoneCallController.kt` (fixed, not just merged)

This was the one place a clean textual merge would have shipped a real,
silent bug. B added a `callSource` parameter to `CallManager.placeCallDetailed()`,
defaulting to `"SCHEDULED"`. A's `PhoneCallController.call()` -- written
before that parameter existed -- calls `placeCallDetailed()` with named
arguments and no `callSource`, so it would compile fine against B's new
signature and silently inherit the `"SCHEDULED"` default. Every real,
free-dial call placed from the Phone module would then be mislabeled
`SCHEDULED` in History, the Execution Trace, and Diagnostics -- exactly the
kind of wrong-source bug the spec's `callSource = MANUAL or SCHEDULED`
requirement exists to prevent.

**Fix applied**: `PhoneCallController.call()` now explicitly passes
`callSource = "MANUAL"`. KDoc updated to explain why. This was the only
source change in this merge beyond reconciling the two zips' own content --
everything else is either "take A," "take B," or "splice both verbatim."

## 4. REQUIREMENT-BY-REQUIREMENT CONFIRMATION

Re-read the actual merged code (not assumed from either zip's own docs) to
confirm each spec point holds in the *combined* app:

- **OFFHOOK/retry**: `CallExecutionManager.classifyCallEnd()` only checks
  whether OFFHOOK was ever observed at all -- duration no longer gates
  success/failure anywhere (`BRIEF_OFFHOOK_DIAGNOSTIC_MS` only adds a
  "(brief)" hint to the diagnostic string). Disconnect reason is reported as
  literal `UNKNOWN` rather than guessed. `retryDelaySecondsFor()`'s
  non-retryable set is limited to structural failures (bad number, missing
  permission, bad SIM account, and the four structural AI Voice codes);
  everything else -- including a short-then-nothing call -- retries at the
  task's own normal configured interval, never a special "was brief" path.
- **Duplicate-call protection covers both manual paths**: B's
  `CallExecutionStore` active-attempt guard protects the Scheduler engine and
  `callNow()`. Separately, `CallManager.placeCallDetailed()` itself checks
  `CallStateManager.current(context)` for `RINGING`/`OFFHOOK` and returns
  `DEVICE_CALL_BUSY` before placing any call -- this protects *every*
  caller, including the Phone module's direct dial, with no extra code
  needed for that path.
- **Manifest**: zero duplicate activities, receivers, services, or
  permissions (checked directly against the final merged manifest, not
  inferred). Every manifest-declared class resolves to a real file.
- **No duplicate top-level Kotlin declarations** anywhere in the merged
  `app/src/main/java` tree (checked across all 30 files, not just the ones
  touched by this merge).
- **Back navigation**: `PhoneActivity` is launched with a plain
  `startActivity()` and has no `taskAffinity`/custom `launchMode` in the
  manifest and no `onBackPressed` override (its own KDoc says so explicitly)
  -- default back-stack behavior returns to Home. Schedule/Menu are
  in-WebView `nav()` calls, unchanged by this merge either way.

## 5. FLAGGED FOR YOUR DECISION -- NOT RESOLVED EITHER WAY

The spec states, under **IMPORTANT MANUAL-CALL RULE**: *"Manual CALL must
NOT modify or consume an existing scheduled occurrence. It must not
advance/cancel/retry the schedule unless the user explicitly performs a
Scheduler action."*

B's `callNow()` (the new per-row "CALL" button on an existing schedule) treats
a manual trigger as attempt 1 of a fresh cycle and runs it through the full
`finalize/retry/next-slot` pipeline -- so a successful manual call on a
recurring schedule **does** advance it to its next slot, the same as a
successful alarm-driven call would. B's own `V1.1.0-CALL-ENGINE-INTEGRATION.md`
(section 3) already flags this as a deliberate judgment call, not an
oversight, precisely because the spec doesn't fully resolve whether tapping
CALL on a specific schedule row counts as "explicitly performing a Scheduler
action."

I have **not** changed this behavior in either direction -- it's a product
decision about what "manual call" should mean for a recurring schedule, not
a correctness bug like section 3. If you want manual calls to leave a
schedule's cycle completely untouched instead, that needs new work: running
the attempt against a non-persisted snapshot of the task (so trace/history
still records it) without writing `attemptCount`/`status`/`nextTrigger`
mutations back to `TaskStore`. Happy to build that if it's what you want --
just flagging that today's merged behavior matches B's as-built feature,
which is one reasonable reading of the rule, not the only one.
