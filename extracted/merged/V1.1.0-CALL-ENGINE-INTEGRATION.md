# V1.1.0 Common Call Engine Integration (Phone / Scheduler / AI Voice)

This package starts from the V1.0.9-AI-VOICE-BACKEND-FIX bundle plus three
standalone files (CallReceiver.kt, BootReceiver.kt, CallExecutionManager.kt)
supplied alongside it. **Those three files were not simply layered on top of
the zip** -- they had diverged from it, each fixing bugs the other did not:

- The zip has AI Voice's granular failure codes (`AI_VOICE_CONFIG_MISSING`,
  `AI_VOICE_AUTH_FAILED`, etc.) and the non-retryable-set additions those
  enable, but still runs `AiVoiceCallClient.create()` inline on the main
  thread (a real `NetworkOnMainThreadException` bug) and still uses the old
  `MIN_CONNECTED_OFFHOOK_MS` hard gate that misclassifies short, genuine
  calls as failures.
- The standalone files fix the main-thread network bug, remove the OFFHOOK
  duration gate, and fix `BootReceiver` silently dropping past-due tasks --
  but were missing the granular AI Voice codes entirely (flat
  `AI_VOICE_REQUEST_FAILED` only).

`CallReceiver.kt` and `CallExecutionManager.kt` were merged by hand, keeping
every fix from both sides (confirmed line-by-line against
`V1.0.9-AI-VOICE-BACKEND-FIX.md`'s own description of its changes).
`BootReceiver.kt` had no conflict and was adopted as-is.

## 1. WHAT THIS TASK ADDED ON TOP OF THE MERGE

The merge alone doesn't satisfy the integration spec's Section 2 (manual
calling) or Section 5 (common execution identity) -- those needed real,
new work, not just reconciliation:

- **A genuine manual "call now" path.** Before this change, every real call
  -- including a schedule's own "Start" button -- went through
  CallScheduler/AlarmManager, and the only calling action independent of a
  schedule (per-row "dialer") just opened the system Phone app rather than
  placing a call. There was no way to place a real call immediately without
  the Scheduler, as the spec requires for MANUAL. `CallNow` (new
  `@JavascriptInterface` bridge method, new "CALL" button next to Start/
  Stop/Edit/Msg/Dial/Del on each schedule row) now does this, through the
  same engine, with no alarm involved.
- **One shared call-attempt engine.** `CallReceiver.handleCallAttempt`'s
  tail -- the callEnabled check, the active-call guard, the AI_VOICE
  background-thread dispatch, `beginAttempt`, `CallManager.placeCallDetailed`,
  and the post-call bookkeeping -- was extracted into
  `CallExecutionManager.executeCallAttempt()`. `CallReceiver` now only
  handles what's genuinely alarm-specific (staleness, pause state,
  task.status) and calls into the shared function; the manual bridge method
  calls the exact same function directly.
- **A `callSource` field** ("MANUAL" or "SCHEDULED") threaded through
  `ExecutionTraceStore.TraceEvent`, `CallExecutionStore.ActiveCall`, and
  `TaskStore`'s history JSON, so History, the per-task timeline, and the
  Execution Trace can all show which entry point produced a given attempt --
  every added parameter defaults to `"SCHEDULED"`, so no existing call site
  needed to change to keep compiling. A retry always shows as SCHEDULED
  once it actually fires, regardless of whether the attempt that triggered
  it was manual -- it always runs through the alarm.

  `executeCallAttempt()` entry point and `callSource` threaded through every
  function (`beginAttempt`, `handleImmediateFailure`, `completeWithoutCall`,
  `finalizeAttempt`, `completeOrScheduleNext`, `notifyAfter`,
  `markSchedulerFailure`, `updateTaskState`, plus the AI Voice helpers moved

  through `log()`/`toJson`/`fromJson`/`formatLine`.

  now includes `"callSource"` in the JSON it hands to the WebView (this was

- `auto_call_ui.html` -- one new per-schedule "CALL" button (`i-phone` icon,
  same style as its siblings) wired to `NativeBridge.callNow()` behind a

  like the wrong default); a `Source` badge added next to the existing
  `Local:` badge in the History tab; `source=` added to the Execution
  Trace's per-line context string; `source` added to the per-task timeline's
  sub-line. No layout, color, or navigation-structure changes.
- `CallExecutionManagerTest.kt` -- rewritten for the merged `classifyCallEnd`
  (2 outcomes now, not 3 -- `CALL_OFFHOOK_TOO_BRIEF` no longer exists as a
  produced value), added coverage for `describeCallEnd` (previously
  untested), and added the 4 new AI Voice codes to the non-retryable test
  and 3 more to the transient-codes test.
- Version bump: `versionCode` 109->110, `versionName` "1.0.9"->"1.1.0"
  (`build.gradle.kts`, `VERSION.txt`, `BackupManager.BACKUP_VERSION`,
  `Diagnostics`'s reported version, the backup filename and diagnostic-log

  read/compared anywhere in `BackupManager.kt`), so bumping it doesn't touch

(`CallScheduler.kt`), `ScheduleCalculator.kt`, the AI Voice backend client

(the "CALLS" module), `Schedule`, `AI Voice`, and `Diagnostics` navigation
entry points were already wired correctly and needed no changes.

## 3. A DELIBERATE INTERPRETIVE CALL WORTH FLAGGING

The spec's Section 1 lists MANUAL / SCHEDULED / AI_VOICE as one flat set of
"call sources." This app already has an orthogonal, pre-existing
`task.executionMode` field (`NORMAL_SIM` / `AI_VOICE`) governing *how* a
call is carried out, separate from *what triggered* a given attempt. Rather
than collapsing that into one field, `callSource` only distinguishes
MANUAL vs. SCHEDULED (the trigger); `executionMode` still separately governs
NORMAL_SIM vs. AI_VOICE (the mechanism). An AI Voice attempt's history/trace
rows carry both -- `eventType="AI_VOICE"` already made that mechanism
distinguishable before this change, and now `source` shows whether it was
triggered manually or by its own schedule too. This preserves strictly more
information than force-fitting a single three-way field would have.

Also worth flagging: `callNow` treats every manual call as a fresh attempt 1
of a new cycle (mirroring the existing `startTask()`'s "start over"
semantics) and lets it run through the same finalize/retry/next-slot logic
as any other attempt. On a recurring schedule, a successful manual call
advances it to its next slot, same as a successful scheduled one would --
there is no separate "manual only, don't touch the schedule" outcome path.
This was a judgment call in an area the spec didn't fully resolve; flagging
it in case a "manual call has zero effect on the schedule's own cycle"
behavior is actually what's wanted instead.

## 4. TESTING

**NOT VERIFIED: Kotlin compilation, Android lint, Android unit tests, and
the debug APK build.** This environment has no Android SDK, no `gradlew`
wrapper in this bundle, and no network access to obtain either (confirmed:
`dl.google.com` returns `host_not_allowed`). Please run this through the
project's actual CI or a local `gradle` build before relying on it -- per
this project's own memory, GitHub Actions (JDK 17, Gradle 8.9) is the
authoritative build environment, not a sandbox like this one.

What WAS done in place of a real compile:

- Every changed/created Kotlin file was read back in full after editing.
- Every new or changed identifier (`executeCallAttempt`, `callSource`,
  `callNow`, `beginAttempt`, `handleImmediateFailure`, `completeWithoutCall`,
  `placeCallDetailed`, `BRIEF_OFFHOOK_DIAGNOSTIC_MS`, etc.) was grepped
  across the whole source tree to confirm it's defined exactly once and
  every call site matches its current signature, including across the
  Kotlin/JSON bridge boundary into the WebView JS.
- One real gap was caught this way before it shipped:
  `getExecutionTraceJson()` in `MainActivity.kt` manually re-serializes
  `TraceEvent` field-by-field rather than reusing `ExecutionTraceStore`'s
  own JSON -- adding `callSource` to the data class alone would have left
  the WebView's `e.callSource` permanently `undefined`. Fixed by adding the
  field to that serialization too.
- Brace/parenthesis counts were checked (string/comment-stripped) on every
  touched Kotlin file; all balance. `MainActivity.kt` shows a pre-existing
  41/40 curly and 92/91 paren "imbalance" under this crude check, confirmed
  present and identical in the untouched original file from the zip before
  any edit -- a false positive of the check itself (almost certainly a
  char-literal or escape sequence the check's regex doesn't handle), not a
  real defect, and not something this change introduced or altered.
- The HTML's one inline `<script>` block was extracted and run through
  `node --check` after every edit: valid JavaScript syntax, both times.
- `CallExecutionManagerTest.kt`'s new/changed assertions were traced by hand
  against the actual merged implementation line-by-line (not just written
  and assumed correct).

This is real verification of what could be verified without the Android
toolchain. It is not a substitute for `./gradlew testDebugUnitTest` and
`:app:assembleDebug`, and Kotlin compilation itself remains unconfirmed.

## 5. SUGGESTED ON-DEVICE TEST PASS

Per the spec's own test matrix, once this builds: manual call-now on a
NORMAL_SIM task (answered, short/brief answered, declined, no SIM); manual
call-now on an AI_VOICE task with the backend configured and with it blank;
manual call-now while a scheduled call is already active (should be
blocked, `CALL_BLOCKED_ACTIVE_CALL`); manual call-now on a paused schedule
set (should be blocked); a manual call-now on a WEEKLY schedule that
succeeds, confirming it advances to its own next slot rather than
disappearing; History/per-task timeline/Execution Trace all showing
`Source: MANUAL` for these versus `SCHEDULED` for an ordinary alarm-driven
call; reboot recovery and the existing retry/backoff behavior, to confirm
nothing regressed there.
