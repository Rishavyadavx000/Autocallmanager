# V1.0.9 AI Voice Backend / Admin Catalog Separation Fix

This package is based on the V1.0.9 COMPLETE-COMBINED-FINAL bundle (CI/Admin fix
already applied). It addresses the AI Voice backend configuration issue.

## 1. ROOT CAUSE

`AiVoiceCallClient.kt` (the class that sends the AI Voice call request) read
its base URL from `SettingsStore.adminCatalogUrl()` -- the **same** setting
used by the Admin Prompt Catalog (`PromptStore.kt`), with no independent "AI
Voice Backend" concept anywhere in the app: not in `SettingsStore`, not in
`Diagnostics`, not in the Settings screen.

Reusing that URL is not itself wrong: `admin-server/src/server.js` really does
serve both `/v1/prompts` (catalog) and `/v1/voice/calls` (AI Voice) from the
one server, as separate documented paths -- confirmed by reading the actual
route table, not assumed. What was missing is that the Admin Catalog URL
field's own "blank = local-only" behavior is a *valid, working* state for the
catalog, but the Settings screen had no separate signal that the same blank
field also means AI Voice calls cannot be placed at all. Someone could
configure Gemini, see it come back ONLINE, leave the catalog URL blank
because they're happy with the bundled catalog, and have no indication
anywhere in Settings that this also disables AI Voice calling.

A second, compounding bug: every AI Voice failure -- whether the URL was
blank, the app key was wrong, the backend was down, or the recipient had
opted out -- collapsed into one generic `AI_VOICE_REQUEST_FAILED` code, and
`CallExecutionManager.retryDelaySecondsFor()` did not treat that code as
non-retryable. So a structurally-unfixable-by-waiting failure (no URL
configured) retried at the normal interval anyway, every time producing the
exact same failure, until `maxAttempts` was exhausted -- this is the
`AI_VOICE_REQUEST_FAILED` / `RETRY_SCHEDULED` loop from the original report.

## 3. EXACT CHANGES

**AiVoiceCallClient.kt** -- `create()` now returns a `code` alongside
`ok`/`message`: `CONFIG_MISSING` (blank URL), `INVALID_URL`, `AUTH_FAILED`
(HTTP 401), `REJECTED` (HTTP 403 consent/safety-gate block, or any other
4xx), `SERVER_ERROR` (5xx), `OFFLINE` (network exception), or the previous
`REQUEST_FAILED` as a fallback. Added `checkHealth()`, a new unauthenticated
`GET {baseUrl}/v1/health` reachability check (that route already existed on
the server and required no app key) returning `ONLINE`/`OFFLINE`/
`SERVER_ERROR`/`CONFIG_MISSING`/`INVALID_URL`.

**CallReceiver.kt** -- the `AI_VOICE` branch now sets
`liveStatus`/`lastResult` to `"AI_VOICE_" + code` instead of the flat
`AI_VOICE_REQUEST_FAILED`, and logs a new `AI_VOICE_REQUEST`
`ExecutionTraceStore` stage (PASS on dispatch success, FAIL with the specific
code+message on failure). It also now logs `CALL_EXECUTION_BEGIN` for this
branch, which it previously skipped entirely (that stage was only logged on
the NORMAL_SIM path).

**CallExecutionManager.kt** -- `retryDelaySecondsFor()` adds
`AI_VOICE_CONFIG_MISSING`, `AI_VOICE_INVALID_URL`, `AI_VOICE_AUTH_FAILED`,
`AI_VOICE_REJECTED` to the non-retryable set (returns `Long.MAX_VALUE`, same
as `INVALID_NUMBER`/`CALL_NOT_PERMITTED` already did). `AI_VOICE_OFFLINE`,
`AI_VOICE_SERVER_ERROR`, and the fallback `AI_VOICE_REQUEST_FAILED` still
retry at the task's configured interval, unchanged.

**ExecutionTraceStore.kt** -- added `Stage.AI_VOICE_REQUEST`, documented as
the branch taken instead of `PHONE_ACCOUNT_RESOLVED` / `PLACE_CALL` /
`CALL_STATE_CALLBACK` for AI Voice tasks.

**SettingsStore.kt** -- added `aiVoiceBackendConfigured()`,
`aiVoiceBackendStatus()`, `aiVoiceBackendLastTest()`,
`aiVoiceBackendLastError()`, `setAiVoiceBackendTestResult()`. These are
backed by three new pref keys, kept deliberately separate from
`PROMPTS_SYNC_STATUS` even though both read `ADMIN_CATALOG_URL`. Changing
`ADMIN_CATALOG_URL` via `set()` now also resets the AI Voice Backend's cached
status (previously only the prompt-sync status was reset), so a stale result
from a previous URL can't linger.

**Diagnostics.kt** -- added `aiVoiceBackendConfigured` and
`aiVoiceBackendStatus` fields, distinct from the existing
`adminCatalogConfigured`.

**MainActivity.kt** -- `getSettingsJson()` exposes the four new
`aiVoiceBackend*` fields to the WebView. Added a `testAiVoiceBackend()`
`@JavascriptInterface` bridge method (async, mirrors the existing
`refreshPromptCatalog()`/`testAiConnection()` pattern: background thread,
JS callback via `onAiVoiceBackendTested`, then `refreshWebView()`). Reworded
the Admin Catalog URL dialog to state plainly that the same URL is also used
for AI Voice calls, and that leaving it blank disables AI Voice calling.

**auto_call_ui.html** --
- Three new Settings rows under Administration: "AI Voice Backend"
  (CONFIGURED/NOT CONFIGURED), "Test AI Voice Backend" (tappable, shows
  ONLINE/OFFLINE/AUTH FAILED/etc.), "Last Checked".
- New JS: `testAiVoiceBackend()`, `onAiVoiceBackendTested()`,
  `updateVoiceBackendUI()` (called from `updateSettingsUI()`).
- Reworded the AI Voice mode hint in the schedule wizard to point at
  Settings -> Administration specifically, instead of a generic "configured
  backend/provider."
- `setStatusText()`'s red-badge list widened to include the new failure
  codes (`AUTH_FAILED`, `INVALID_URL`, `REJECTED`, `OFFLINE`,
  `CONFIG_MISSING`), so they render as failures rather than falling through
  to the default amber/pending color.
- The Diagnostics modal's bad-status list widened the same way, and gained
  an "AI Voice Backend" row. While touching this list, also added
  `AUTH_ERROR`/`SERVER_ERROR`/`RATE_LIMITED`, which were already red in
  `setStatusText` for Gemini but were missing here, so a Gemini
  `SERVER_ERROR` would have rendered as a false PASS in this specific modal
  -- a pre-existing inconsistency, fixed while already in this code.
- The per-task timeline's failed/done/active classification relied on the
  free-text result message containing the substring `FAILED`, which is true
  for the old generic code but not for most of the new specific ones. It now
  also checks the reliable `liveStatus` code directly for any
  `AI_VOICE_*` status other than `AI_VOICE_REQUESTED`.

**.github/workflows/main.yml** -- bumped `actions/upload-artifact@v4` to
`@v7` (current major version, confirmed via web search; matches the
already-current major-version style of every other action pin in this file)
in all three places it appeared. This was the item flagged from the previous
CI/Admin fix pass and was otherwise untouched.

## 6. AI VOICE BACKEND STATUS

Now a distinct, independently-surfaced concept for the first time:
`SettingsStore.aiVoiceBackendConfigured()` / `aiVoiceBackendStatus()`,
reported in `Diagnostics`, the Settings screen (new rows + live "Test AI
Voice Backend" check against `/v1/health`), and in `liveStatus`/`lastResult`
on the task itself. It is still backed by the same `ADMIN_CATALOG_URL`
setting as the catalog, because that is architecturally correct for this
backend (verified against `admin-server/src/server.js`), not because the two
features are the same thing.

## 7. SECURITY STATUS

Not weakened. No key, secret, or credential is logged or hardcoded by these
changes. `X-App-Key` continues to be sent only as a request header, over
HTTPS (enforced at save time in `SettingsStore.set()`, unchanged). The new
`checkHealth()` call intentionally sends no app key, matching the server's
own unauthenticated `/v1/health` route -- it proves reachability only, not
that the app key is valid; that still only surfaces through `AUTH_FAILED` on
a real `create()` attempt, since no dedicated authenticated ping endpoint
exists on the server to test that separately.

## 13. REMAINING LIMITATIONS

- **Kotlin compilation, Android lint, Android unit tests, and the debug APK
  build are NOT VERIFIED** -- this environment has no Android SDK and no
  network access to install one. Please run this bundle through the actual
  GitHub Actions workflow (or a local `gradle` build) before relying on it.
- `checkHealth()` can only prove the backend URL is reachable, not that the
  app key is valid -- there is no unauthenticated-but-key-checking endpoint
  on the server to test that separately. An app-key problem still only
  surfaces as `AUTH_FAILED` the next time a real AI Voice call is attempted.
- Once the backend accepts an AI Voice request, Android has no further
  visibility into the real call outcome (that happens server-side via
  Twilio + webhooks). `AI_VOICE_REQUESTED` is deliberately the last state
  logged for a successful dispatch -- this is an inherent property of the
  server-originated call architecture, not something this fix could or
  should paper over.
- Two pre-existing, narrower cosmetic gaps were found but deliberately left
  alone as out of scope (neither is a regression introduced by this fix):
  the cross-task History tab categorizes rows by exact `eventType` string
  and has no "AI Voice" bucket, so `AI_VOICE`-type history rows show "Not
  enabled" under Call/Voice/AI there even though they display correctly in
  the per-task timeline this fix did touch; and the Dashboard's "recent
  activity"/today's-count regexes don't recognize several AI Voice failure
  codes (e.g. `CONFIG_MISSING`, `OFFLINE`, `REJECTED`) as failures, the same
  way they already miss several pre-existing NORMAL_SIM codes like
  `INVALID_NUMBER` -- a broader, pre-existing pattern-matching limitation
  affecting many status codes, not specific to this fix.
- Real OEM background-execution restrictions (Realme/Oppo/etc.) were not
  something this fix touched and cannot be verified from source alone --
  this remains a real-device-only concern, unchanged from before.
